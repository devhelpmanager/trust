## 0. Как работать с этим ТЗ

1. **Прочитай ТЗ целиком до начала работы.** Затем изучи макеты в репозитории (раздел 2) и составь
   инвентарь: какая секция какого макета становится каким блоком или шаблоном (раздел 19, этап 0).
2. **Макеты — источник истины по внешнему виду.** ТЗ — источник истины по архитектуре и поведению
   в админке. Если они противоречат друг другу или чего-то не хватает, остановись и задай заказчику
   вопрос списком. Не придумывай решения молча.
3. **Не придумывай контент.** Тексты, цифры, имена и заглушки в квадратных скобках из макетов
   попадают только в демо-контент (раздел 17), а не в код темы.
4. **Работай этапами** (раздел 19). После каждого этапа запускай проверки (раздел 18), делай коммит
   и пиши короткий отчёт: что сделано, что проверено, какие вопросы остались.
5. Всё, что видит посетитель сайта (тексты, картинки, видео, цифры, ссылки), должно редактироваться
   в админке. В коде темы остаётся только вёрстка, стили, логика и служебные строки интерфейса.

## 1. Цель и результат

**Цель:** перенести готовый дизайн сайта агентства в собственную тему WordPress так, чтобы:

- каждая секция каждого макета была отдельным блоком визуального редактора (Gutenberg) с
  вёрсткой в коде темы и контентом в полях;
- при создании страницы можно было выбрать **тип страницы**. Тип сразу подставляет нужный
  набор блоков, а редактор добавляет, удаляет и переставляет блоки и наполняет их текстом,
  картинками и видео;
- у каждой страницы, записи, кейса, ответа, сотрудника, рубрики и тега можно было задать
  **SEO title, meta description и H1**, а у каждой картинки — **alt**;
- на сайте была корректная **микроразметка schema.org**: FAQ, услуги, компания, хлебные
  крошки, статьи, ответы на вопросы, сотрудники, видео;
- сайт выглядел и вёл себя как макеты на всех ширинах экрана от 280 до 1440 px и выше.

**Результат (что сдаётся):**

| Что | Где |
|---|---|
| Тема WordPress `trust` | `wp-theme/trust/` в репозитории `devhelpmanager/trust` |
| Демо-контент и команда его импорта | `wp-theme/trust/demo/` + WP-CLI команда (раздел 17) |
| Автотесты (Playwright + PHP-проверки) | `wp-theme/tests/` |
| Инструкция по установке и разработке | `wp-theme/README.md` |
| Инструкция для редактора сайта (на русском) | `wp-theme/trust/docs/instrukciya-redaktora.md` |
| Инвентарь «макет → блок/шаблон» | `wp-theme/docs/inventory.md` |

Работа ведётся в ветке `wp-theme` с pull request в `main`.

### 2.2. Формат исходников `*.dc.html`

- Разметка блока внутри `<x-dc>…</x-dc>`, стили — в `<helmet><style>…</style></helmet>` и в
  атрибутах `style`.
- `{{имя}}` — подстановка значения из логики; `<sc-for list="{{…}}" as="x">` — цикл;
  `<sc-if value="{{…}}">` — условие; `<dc-import name="Header" …>` — вложенный компонент,
  атрибуты — его параметры.
- Логика — класс `Component extends DCLogic` в `<script type="text/x-dc">`: метод
  `renderVals()` возвращает значения для подстановок, состояние меняется через `this.setState`.
- В исходниках картинки подключены как `/_blob/<id>`. Те же картинки с понятными именами лежат в
  папках `images/` экспортов. Соответствие `blob → файл` видно, если сравнить `src` в исходнике и
  в HTML-экспорте того же блока.

**Как переносить:**

- Inline-стили превращаются в классы. Именование — BEM-подобное с префиксом блока, например
  `.b-faq__item`.
- Значения цветов, размеров, отступов, скруглений и медиазапросов сохраняются **точно**.
- Логика `renderVals/setState` переписывается на чистый JavaScript для фронтенда.
- Данные, которые в макете лежат массивами в логике (вопросы FAQ, кейсы, тарифы и т. п.),
  становятся полями блока или записями типов данных (раздел 5).

### 2.3. Дизайн-токены (кратко, полный список — `seo-bloki/opisanie-blokov.txt`)

- Индиго `#1E1B4B` (шапка, подвал, тёмные первые экраны), основной фиолетовый `#6D28D9`,
  тёмно-фиолетовый `#5B21B6`, лавандовые фоны `#F8F5FF`, `#F3EEFF`, `#EEE7FE`, рамки `#E0D7F5`,
  `#D9CFF2`, текст `#0E0B14`, `#2B2733`, `#5A5566`.
- Шрифты: **Unbounded** 500/600 (заголовки, крупные цифры), **Onest** 400–700 (текст,
  интерфейс), **JetBrains Mono** 500 (надзаголовки, номера, служебные подписи).
- Контент до 1200 px, текстовая колонка до 760 px, боковые отступы `clamp(20px, 4vw, 48px)`.
- Основные контрольные точки из макетов: 1180 px (меню → бургер), 1024/1023, 960, 800, 760,
  640, 600, 520, 480, 340 px. Бери их из исходников конкретного блока.
- Кликабельные элементы ≥ 44 px, шрифт полей ввода ≥ 16 px, текст ≥ 12 px.

Все токены оформи CSS-переменными в `:root` и продублируй в `theme.json` (палитра и
шрифты для редактора).

## 3. Ключевые принципы

1. **Вёрстка в коде, контент в админке.** В PHP-шаблонах и `render.php` блоков нет ни одного
   видимого посетителю текста, картинки или ссылки из макета. Исключение — служебные строки
   интерфейса: «Далее», «Назад», сообщения валидации, «Страница N из M», aria-подписи. Их
   оборачивают в `__()` / `esc_html__()` с текстовым доменом `trust`, исходный язык строк —
   русский. Заголовки секций, тексты кнопок и подписи, которые в макете можно поменять по
   смыслу (например «Частые вопросы», «Заказать аудит»), — это **поля** со значением по
   умолчанию из макета. Заголовки и подписи, которые выводят шаблоны, а не блоки («Похожие
   кейсы», «Читайте также», «Другие ответы», «Хочу так же» и т. п.), редактируются на вкладке
   «Настройки сайта → Тексты шаблонов».
2. **Одна сущность — одно место ввода.** Кейс, отзыв, сотрудник, вакансия, вопрос, статья
   вводятся один раз как запись своего типа. Блоки на страницах выбирают их из базы, а не
   копируют текст.
3. **Ровно один H1 на странице.** H1 выводит первый экран (hero) или шаблон и берёт текст из
   SEO-поля «H1» (если оно пустое — из заголовка записи). Во всех блоках заголовки секций — H2,
   заголовки карточек — H3. В редакторе в блоке «Заголовок» доступны только уровни H2–H4.
4. **Визуальное соответствие макетам.** Те же отступы, размеры, цвета, анимации, поведение на
   всех ширинах. Расхождения допустимы только там, где макет показывает заглушку («место под
   Яндекс Карту», «место под капчу»).
5. **Минимум зависимостей.** Обязательный плагин — только **Secure Custom Fields (SCF)** из
   каталога WordPress.org (бесплатный форк ACF с тем же API: `get_field()`, блоки, повторители,
   гибкий контент, страницы настроек). Без jQuery на фронтенде. Без конструкторов страниц.
   Без внешних CDN.
6. **SEO, микроразметка и формы реализуются в теме** и не требуют SEO-плагинов и плагинов форм.
   Если на сайте всё же активирован Yoast SEO или Rank Math, тема отключает собственный вывод
   title/description/OG/JSON-LD, чтобы не было дублей, и показывает предупреждение в админке.
7. **Только русский язык**, мультиязычность не нужна.
8. **Данные посетителей не уходят третьим лицам без согласия.** Шрифты локальные, аналитика и
   встраиваемые видео и карты загружаются только после согласия на cookie или по клику.

## 4. Технические требования

### 4.1. Окружение

- WordPress 6.6+ (проверить на последней стабильной версии), PHP 8.1+ (проверить на 8.3),
  MySQL 8 / MariaDB 10.6+.
- Плагин Secure Custom Fields, последняя версия. Если SCF не активирован, тема не падает:
  показывает в админке уведомление со ссылкой на установку, а блоки и поля не регистрирует.
- Локальная разработка: `@wordpress/env` (Docker) или WordPress Playground CLI. Если ни то, ни
  другое недоступно — PHP + SQLite Database Integration. Опиши выбранный способ в README.

### 4.2. Тип темы

- **Классическая PHP-тема с блочным редактором для контента** (не блочная FSE-тема).
  Шаблоны страниц, шапка, подвал, архивы — PHP-файлы. Редактор сайта (Site Editor), библиотека
  шрифтов, каталог блоков и встроенные паттерны ядра отключены.
- `theme.json` версии 3: палитра и шрифты из токенов, отключены свои цвета, градиенты,
  размеры шрифтов, дуотон и произвольные отступы, чтобы редактор не мог «сломать» дизайн.
- Стили редактора подключают те же CSS блоков, чтобы превью в редакторе совпадало с сайтом.

### 4.3. Код

- PHP: WordPress Coding Standards (проверка `phpcs` с WPCS), строгая типизация там, где
  уместно, префикс функций и хуков `trust_`, пространство имён `Trust\` для классов.
- Безопасность: экранирование при выводе (`esc_html`, `esc_attr`, `esc_url`, `wp_kses_post`),
  очистка при вводе, nonce и проверка прав в админ-действиях, подготовленные SQL-запросы,
  никакого `eval` и выполнения пользовательского кода.
- JavaScript: современный ES (без транспиляции), модули по блокам, никаких фреймворков на
  фронтенде. Для работы темы **сборка не требуется**: в репозитории лежат готовые CSS и JS.
  Минификацию можно добавить отдельным необязательным скриптом.
- CSS: обычный CSS с переменными, без препроцессора (можно PostCSS для минификации, но тема
  работает и без сборки). Каждый блок — свой файл стилей, общий файл — только токены, базовая
  типографика, сетка, шапка, подвал, кнопки и поля.

### 4.4. Структура темы (ориентир)

```
wp-theme/trust/
  style.css, functions.php, theme.json, screenshot.png
  inc/                 — классы и модули: setup, assets, cpt, taxonomies, options, seo, schema,
                         breadcrumbs, forms, cookies, likes-views, editor, page-types, rest, cli
  template-parts/      — header, footer, breadcrumbs, cards (post, case, answer, review…),
                         hero-архивов, pagination, cookie-banner, callback-modal
  templates/           — шаблоны страниц (типы страниц, раздел 6)
  blocks/<name>/       — block.json, render.php, fields.php, style.css, view.js (если нужен),
                         example.php (данные для превью в списке блоков)
  assets/css/ assets/js/ assets/fonts/ assets/icons/ (SVG-спрайт) assets/img/ (декор)
  demo/                — демо-контент и медиа для импорта
  docs/instrukciya-redaktora.md
  single.php, single-case.php, single-question.php, single-team.php, home.php, category.php,
  tag.php, archive.php, author.php, search.php, 404.php, page.php, index.php, comments.php
```

Поля регистрируются в PHP через `acf_add_local_field_group()` (файл `fields.php` рядом с
блоком или в `inc/fields/`). Тогда структура полей лежит в git и не зависит от базы.

Блоки регистрируются через `register_block_type( __DIR__ . '/blocks/<name>' )`, в
`block.json` указывается ключ `"acf": { "mode": "preview", "renderTemplate": "render.php" }`.
Если установленная версия SCF это не поддерживает, используй `acf_register_block_type()` с
теми же параметрами. Пространство имён блоков — `trust/`.

## 5. Модель данных

### 5.1. Типы записей

Названия в админке — на русском, у каждого типа своя иконка в меню. Ярлыки (slug) URL ниже —
значения по умолчанию. Их можно поменять в «Настройках сайта → Адреса»; после смены правила
перезаписи сбрасываются автоматически.

| Тип (`post_type`) | В админке | URL | Публичный | Что хранит |
|---|---|---|---|---|
| `page` | Страницы | иерархия страниц | да | Все страницы сайта, тип страницы выбирается (раздел 6) |
| `post` | Статьи | `/blog/%postname%/` | да | Статьи блога |
| `case` | Кейсы | `/portfolio/<slug>/` | да | Кейсы портфолио |
| `review` | Отзывы | — | нет (только вывод в блоках) | Текстовые и видеоотзывы, благодарственные письма |
| `team` | Сотрудники | `/komanda/<slug>/` | да | Сотрудники, страница сотрудника = страница автора |
| `vacancy` | Вакансии | — | нет | Вакансии для страницы «Карьера» |
| `question` | Вопросы SEO | `/seo/voprosy/<slug>/` | да | Вопрос читателя и ответ специалиста |
| `lead` | Заявки | — | нет, только админка | Все заявки из форм сайта (раздел 12) |

Архивы у CPT отключены (`has_archive => false`). Список кейсов, вопросов и сотрудников выводят
обычные страницы с блоками (`/portfolio/`, `/seo/voprosy/`, `/komanda/`). URL записей
вложены в URL этих страниц. Хлебные крошки и подсветка меню учитывают эту связь (раздел 6.4).

Постоянные ссылки статей — `/blog/%postname%/`. У CPT выставлено `with_front => false`,
поэтому префикс `/blog/` к ним не добавляется.

### 5.2. Таксономии

| Таксономия | Для типов | В админке | URL | Назначение |
|---|---|---|---|---|
| `category` | post | Рубрики | `/blog/rubrika/<slug>/` | Рубрики блога |
| `post_tag` | post, question | Теги | `/blog/teg/<slug>/` | Теги блога; общие для статей и ответов (страница тега показывает и то и другое) |
| `service_type` | case, review | Услуги | — (без публичных страниц) | Фильтр «по услуге» в портфолио и отзывах |
| `industry` | case | Отрасли | — | Фильтр «по отрасли» в портфолио |
| `department` | team, vacancy | Отделы | — | Фильтры в «Команде» и «Карьере» |
| `question_topic` | question | Темы вопросов | — | Плашка темы у вопроса («Индексация» и т. п.) |

### 5.3. Поля записей (основное)

Поля, общие для всех публичных типов (страницы, статьи, кейсы, ответы, сотрудники) и для рубрик
и тегов, — **группа «SEO»** (раздел 10.1).

**Статья (`post`):**
- обложка — изображение записи с alt;
- «Главная статья» — флажок: такая статья выводится крупной карточкой («Новая статья») на
  странице блога и рубрики; если не отмечена ни одна, берётся последняя;
- анонс — стандартная «цитата» (excerpt);
- автор — пользователь WordPress, связанный с сотрудником (см. `team`);
- служебные метаполя `trust_views` и `trust_likes` (раздел 13).

**Рубрика (`category`):**
- «Ведёт рубрику» — связь с сотрудником;
- «О рубрике» — WYSIWYG, выводится в раскрывающемся блоке внизу;
- описание — стандартное описание термина (подзаголовок под H1);
- SEO-поля.

**Тег (`post_tag`):** описание (подзаголовок), SEO-поля.

**Кейс (`case`).** Содержимое страницы кейса — блоки (раздел 8.9). Данные для карточек,
фильтров и боковой карточки проекта — поля в боковой панели:
- клиент (название или «[заглушка]»), регион, сроки (с — по), адрес сайта клиента;
- обложка (изображение записи) и скриншот сайта для первого экрана;
- услуги (`service_type`), отрасль (`industry`);
- «Главный кейс» — флажок;
- результаты для карточек — повторитель до 4 строк «значение + подпись»;
- позиции в поиске (для блока «Наши проекты в топе») — повторитель «запрос / позиция в Яндексе
  / позиция в Google», регион и дата проверки;
- команда проекта — связь с сотрудниками;
- отзыв клиента — связь с записью `review` (необязательно).

**Отзыв (`review`):**
- вид: «Текстовый», «Видео», «Благодарственное письмо»;
- автор: имя, должность, компания, фото;
- текст;
- результаты — до 3 строк «значение + подпись»;
- ссылка на оригинал или файл письма;
- для видео — ссылка на видео (YouTube, Rutube, VK Видео или файл) и обложка;
- для письма — изображение письма;
- услуги (`service_type`), дата;
- служебные поля для отзывов из формы: email и телефон автора (не выводятся на сайт), согласие на
  обработку и согласие на распространение с датой и временем.

**Сотрудник (`team`):**
- фото, должность, стаж («опыт в SEO — N лет»), краткое описание для карточки, текст «Об
  авторе» (WYSIWYG), темы («Пишет о») — связь с тегами или свободные строки;
- соцсети — повторитель «сеть (выбор из списка) + ссылка»; иконки соцсетей — официальные
  иконки сетей, а не нарисованные из макета;
- «Руководство» — флажок; порядок вывода;
- связанный пользователь WordPress — нужен для статей и ответов;
- отдел (`department`).

**Вакансия (`vacancy`):**
- отдел, зарплата (текст), формат работы, город, короткое описание;
- разделы описания — повторитель «заголовок + список пунктов» (обязанности, требования,
  условия);
- «Принимаем резюме» — флажок (вакансия выводится только если отмечен).

**Вопрос (`question`):**
- заголовок записи — короткая формулировка вопроса (это и H1);
- полный текст вопроса;
- имя спросившего (публикуется), email спросившего (не публикуется), дата вопроса;
- отвечает — связь с сотрудником, дата ответа;
- тема (`question_topic`), теги (`post_tag`);
- «Статьи по теме из блога» — связь со статьями (если пусто — подбор по общим тегам);
- служебное поле «Ссылка на ответ отправлена» с датой.

Содержимое записи (редактор блоков) — сам ответ специалиста: заголовки, абзацы, списки,
картинки, блок «Как бы поступил я».

### 5.5. Меню

Области меню (`register_nav_menus`):

- **Шапка** — главное меню. Пункты первого уровня с вложенными пунктами превращаются в
  выпадающие списки, как в макете. У вложенного пункта выводится **описание пункта меню**
  (стандартное поле WordPress «Описание») — вторая строка («Технический и SEO-аудит сайта»).
- **Подвал: услуги**, **Подвал: компания**, **Подвал: документы**.
- Структура меню по макету — в Приложении Б. Демо-импорт создаёт меню именно такими.

Текущий пункт меню подсвечивается автоматически по текущей странице и её предкам. Для
записей CPT подсвечивается пункт той страницы, в которую вложен их URL: кейс → «Портфолио»,
вопрос → «SEO» и «Задать вопрос SEO-шнику», статья/рубрика/тег → «Блог». На странице сотрудника,
на документах и на 404 ничего не подсвечивается — как в макетах. Параметр `active` из макетов в
теме не нужен.

## 6. Типы страниц

### 6.1. Как это работает в админке

1. Редактор нажимает «Страницы → Добавить».
2. Открывается окно **«Выберите тип страницы»** со списком типов (название, короткое
   описание, миниатюра). Окно — небольшой скрипт редактора на `wp.data`, без сборки.
3. После выбора:
   - у страницы устанавливается соответствующий PHP-шаблон (`template`);
   - в редактор вставляется **набор блоков по умолчанию** для этого типа в порядке макета.
     Блоки пустые: поля заполнены только значениями по умолчанию вроде заголовков секций, без
     демо-текстов;
   - в боковой панели появляются поля, нужные этому типу (например «Дата редакции» у
     документа).
4. Дальше редактор удаляет, добавляет и переставляет блоки и наполняет их.
5. Тип можно сменить позже в боковой панели («Шаблон»). Блоки при этом не пересоздаются.
   Если страница пустая, предлагается вставить набор по умолчанию.

Для кейсов и ответов набор блоков по умолчанию задаётся через свойство `template` при
регистрации типа записи.

не выводятся. В окне выбора типа у этой страницы показывается подсказка.

### 6.3. Правило первого экрана и H1

- У каждого типа страницы есть свой первый экран. Это блок (раздел 8.1) или часть шаблона
  (архивы, 404, поиск).
- Первый экран выводит хлебные крошки и **H1 из SEO-поля «H1»** (если оно пустое — заголовок
  записи).
- Если редактор удалил блок первого экрана, шаблон выводит стандартную шапку страницы с
  хлебными крошками и H1. Страница без H1 невозможна.
- Блок первого экрана можно добавить на страницу только один раз (`"supports": {"multiple": false}`).

### 6.4. Хлебные крошки

- Строятся автоматически:
  - страницы — по иерархии;
  - статьи — «Главная / Блог / Рубрика / Статья»;
  - кейсы — «Главная / Портфолио / Кейс»;
  - ответы — «Главная / SEO / Вопросы по SEO / Вопрос»;
  - сотрудники — «Главная / Сотрудники / Имя»;
  - рубрика и тег — «Главная / Блог / …».
- У страницы есть поля «Название в хлебных крошках» и «Раздел в хлебных крошках» (подпись +
  ссылка). Раздел подставляется перед текущей страницей, если у неё нет родителя (например,
  «О нас» для страниц раздела, «SEO» для услуг).
- Вёрстка — как в макетах (ссылки ≥ 44 px по высоте). Те же пункты выводятся в микроразметке
  `BreadcrumbList` (раздел 11).
- На главной крошки не выводятся.

## 8. Блоки

### 8.1. Общие правила для всех блоков

- Категория блоков в редакторе — «Блоки сайта». Если блоков много, используй несколько
  категорий: «Первые экраны», «Услуги», «Компания», «Списки», «Формы», «Кейс», «Текст и медиа».
- У каждого блока есть:
  - `example` для превью в списке блоков (демо-значения, а не пустой блок);
  - понятное русское название и описание;
  - иконка;
  - стили и скрипты только для него: `style`, `viewScript` в `block.json`, подключаются только
    на страницах, где блок есть.
- **Общие поля секции** (у всех секций, где это есть в макете): «Якорь» (`id` секции для
  ссылок вида `#calculator`), «Надзаголовок», «Заголовок (H2)», «Вводный текст», «Фон» —
  только те варианты фона, которые есть в макетах для этого блока.
- **Картинки:** поле изображения + поле **«Alt»**. По умолчанию alt берётся из медиатеки; если
  заполнено поле «Alt» в блоке — используется оно. Флажок «Декоративная картинка» ставит
  `alt=""`. Если у содержательной картинки нет alt, в редакторе блока показывается
  предупреждение. Картинки выводятся через `wp_get_attachment_image()` с `srcset`/`sizes`.
  Регистрируй размеры под каждый формат из макетов: обложки 16:9, карточки, скриншоты, фото
  сотрудников. Первый экран грузится с `fetchpriority="high"` и без `loading="lazy"`,
  остальное — лениво.
- **Иконки:** выбор из набора иконок темы — SVG-спрайт, собранный из всех иконок макетов.
  Выбор в поле — список с превью.
- **Ссылки и кнопки:** поле «Ссылка» SCF (адрес, текст, «открывать в новой вкладке»).
- **Списки записей** (кейсы, отзывы, сотрудники, статьи, вакансии, ответы): режим «Автоматически»
  (последние / по услуге / по рубрике, количество) или «Выбрать вручную» (поле связи с
  сортировкой перетаскиванием).
- **Интерактив** (аккордеоны, вкладки, карусели, фильтры, свайп, калькулятор) работает с
  клавиатуры, имеет корректные `aria-*` и уважает `prefers-reduced-motion`, как в макетах.
- **Текстовые области с форматированием** — `InnerBlocks` с ограниченным набором блоков
  (абзац, заголовок H2–H4, список, цитата, картинка, таблица, видео). Это позволяет печатать
  текст прямо в блоке. Простые подписи — текстовые поля.
- Одинаковые по устройству блоки можно объединить в один блок с вариантами вида, если это не
  ухудшает соответствие макетам и удобство редактора. Решение зафиксируй в инвентаре.

#### 8.3.1. Калькулятор (`trust/calculator`)

Повторить 7 шагов, вкладки, прогресс, «Назад/Далее» и экран результата из макета.

**Шаги (все тексты и варианты — поля):**

| Шаг | Что настраивается |
|---|---|
| Регион | Список городов (название + коэффициент, по умолчанию 1), поле «Другой регион» с коэффициентом по умолчанию |
| Запросы | Подпись, подсказка; цена за каждую строку запроса (необязательно, 0 — не учитывать) |
| Контент, Внешняя оптимизация, Репутация | Варианты (повторитель): название, описание, надбавка ₽ в месяц |
| GEO | Варианты «Не адаптируем / Адаптируем» с надбавкой; нейросети (повторитель: название, надбавка) — показываются при выборе «Адаптируем» |
| О сайте | Подписи полей: адрес, тематика, число страниц, возраст сайта, есть ли трафик, цель. На цену не влияют, уходят в заявку |

**Общие поля:**
- базовая цена в месяц, минимальная цена;
- округление (до 1000 ₽ по умолчанию);
- текст результата с подстановкой `{price}` («от {price} ₽ / месяц»), пояснение под ценой;
- кнопка после результата («Обсудить расчёт» → форма заявки или якорь);
- флажок «Форма контактов на экране результата» (по умолчанию выключен). В макете такой формы
  нет: если флажок включён, под результатом выводится компактная форма «имя + телефон + согласие»
  в стиле форм сайта.

**Формула:** `(база + Σ надбавок выбранных вариантов + запросы × цена за запрос) × max(коэффициенты выбранных регионов)`.
Округлить вверх по шагу округления и не опускать ниже минимальной цены.

Если форма контактов включена и посетитель её отправил, ответы калькулятора и результат уходят
в заявку (раздел 12).

## 10. SEO

### 10.1. SEO-поля (группа «SEO»)

Выводятся в боковой панели редактора (или отдельной вкладкой под содержимым) у страниц, статей,
кейсов, ответов, сотрудников. На экране редактирования рубрик и тегов — те же поля.

| Поле | Правило |
|---|---|
| SEO title | Если пусто — по шаблону из настроек (по умолчанию `{title} — {site}`). Счётчик символов, подсветка после 60 |
| Meta description | Если пусто — анонс или первые 160 символов вводного текста первого экрана. Счётчик, подсветка после 160 |
| H1 | Если пусто — заголовок записи |
| Canonical | По умолчанию — сама страница (на страницах пагинации — сама страница пагинации). Поле для своего адреса |
| Индексация | Флажки «noindex» и «nofollow» |
| Open Graph | Заголовок, описание, картинка (если пусто — SEO title, description, обложка или картинка по умолчанию) |
| Предпросмотр сниппета | Как запись будет выглядеть в поиске (title, адрес, description) |

**Alt картинок:**
- поле «Альтернативный текст» в медиатеке обязательно к заполнению при загрузке (подсказка и
  предупреждение);
- в каждом блоке есть своё поле «Alt» (раздел 8.1);
- у обложки записи alt берётся из медиатеки.

### 10.2. Вывод в `<head>`

- `add_theme_support('title-tag')` и фильтры `pre_get_document_title`; description, canonical,
  OG (`og:type`, `og:title`, `og:description`, `og:image` с размерами, `og:url`,
  `og:locale=ru_RU`, `og:site_name`), `twitter:card`.
- Метатег robots — через фильтр `wp_robots`.
- Архивы:
  - рубрика и тег — SEO-поля термина;
  - страница блога — SEO-поля страницы блога;
  - поиск — `noindex`;
  - 404 — `noindex`, title из настроек 404;
  - страницы пагинации — свой canonical и « — страница N» в title.
- **Код ответа 404** — у несуществующих адресов страница 404 отдаётся с HTTP 404 (стандартное
  поведение WordPress — не ломать редиректами).
- **Теги с малым числом материалов** — `noindex, follow`, если материалов (статьи + ответы)
  меньше порога из настроек (по умолчанию 3). Такие теги исключаются из карты сайта.

### 10.3. Карта сайта и robots.txt

- Встроенная карта сайта WordPress (`/wp-sitemap.xml`):
  - включены страницы, статьи, кейсы, ответы, сотрудники, рубрики и индексируемые теги;
  - исключены `review`, `vacancy`, `lead`, пользователи (авторы — это сотрудники), записи с
    `noindex`;
  - у записей — `lastmod` (фильтр `wp_sitemaps_posts_entry`).
- `robots.txt` — виртуальный (фильтр `robots_txt`): текст из настроек + строка `Sitemap:`.
  По умолчанию закрыты `/wp-admin/` (кроме `admin-ajax.php`), `/?s=`, `/search/`.

### 10.4. Адреса

- **Транслитерация ярлыков:** кириллица в ярлыках записей, терминов и именах загружаемых
  файлов автоматически переводится в латиницу (таблица транслитерации в теме, без плагинов).
  Существующие ярлыки при этом не меняются.
- Ярлыки CPT и таксономий — раздел 5.

## 11. Микроразметка schema.org

### 11.1. Общие правила

- Только **JSON-LD**, один `<script type="application/ld+json">` на страницу с `@graph`.
  Сущности связаны через `@id` (`{url}#organization`, `{url}#website`, `{page}#webpage`,
  `{page}#breadcrumb` и т. д.).
- В разметку попадают **только данные, которые видны на странице**. Ничего не выдумывать: если
  поле пустое — свойство не выводится.
- Тексты очищаются от HTML (в `FAQPage`/`QAPage` в ответах допускаются простые теги, разрешённые
  Google: `<p>`, `<br>`, `<ul>`, `<ol>`, `<li>`, `<a>`, `<b>`, `<strong>`, `<i>`, `<em>`).
- Разметка собирается модулем `inc/schema/`. Каждый блок с разметкой (FAQ, видео, тарифы)
  регистрирует свои данные в общем графе страницы, поэтому дублей нет. Если на странице два
  блока FAQ, получается **один** `FAQPage` со всеми вопросами.
- Фильтр `trust_schema_graph` позволяет дополнить или отключить разметку.

### 11.2. Что где выводится

| Где | Сущности | Ключевые свойства |
|---|---|---|
| Все страницы | `Organization` (или `ProfessionalService`, если в настройках выбран этот тип и заполнен адрес), `WebSite` | name, url, logo (`ImageObject`), telephone, email, address (`PostalAddress`), sameAs (соцсети), contactPoint |
| Все страницы, кроме главной | `BreadcrumbList` | Те же пункты, что в видимых хлебных крошках, `position`, `name`, `item` (у последнего пункта `item` можно не указывать) |
| Каждая страница | `WebPage` или подтип (`AboutPage`, `ContactPage`, `CollectionPage`, `ProfilePage`, `FAQPage`, `QAPage`, `SearchResultsPage`) | name (= title), description, url, inLanguage `ru-RU`, isPartOf → `#website`, breadcrumb → `#breadcrumb`, primaryImageOfPage, datePublished, dateModified |
| Блок «Вопрос-ответ» на любой странице | `FAQPage` (страница становится `["WebPage","FAQPage"]`) | mainEntity: `Question` (name) → acceptedAnswer: `Answer` (text). Только вопросы, видимые на странице |
| Тип «Услуга» | `Service` | name (H1), description, url, provider → `#organization`, serviceType, areaServed (из поля, по умолчанию «Россия»), offers: из блока «Тарифы» — `Offer` или `AggregateOffer` (price/lowPrice, priceCurrency `RUB`), только если указана числовая цена |
| Тип «Контакты» | `ContactPage` + расширенная `Organization` | address, geo, openingHoursSpecification (из часов работы), hasMap (ссылка на Яндекс Карты), contactPoint по отделам |
| Тип «О компании» | `AboutPage` + `Organization` | foundingDate, numberOfEmployees, award — из полей, если заполнены |
| Статья | `BlogPosting` | headline, description, image, datePublished, dateModified, author → `Person` (`{сотрудник}#person`), publisher → `#organization`, mainEntityOfPage, articleSection (рубрика), keywords (теги), wordCount, commentCount |
| Ответ на вопрос | `QAPage` | mainEntity: `Question` (name, text, dateCreated, author — `Person` с именем спросившего, answerCount 1) → acceptedAnswer: `Answer` (text, dateCreated, url, author → `Person` специалиста) |
| Страница сотрудника | `ProfilePage` | mainEntity: `Person` (name, jobTitle, image, description, sameAs, worksFor → `#organization`, knowsAbout) |
| Кейс | `Article` | headline, description, image, datePublished, dateModified, author и publisher → `#organization`, about → услуги кейса |
| Блог, рубрика, тег, портфолио, вопросы | `CollectionPage` + `ItemList` | itemListElement: `ListItem` (position, url) записей текущей страницы |
| Блок «Видео», видеоотзывы | `VideoObject` | name, description, thumbnailUrl, uploadDate, duration (если указана), embedUrl/contentUrl |
| Поиск | `SearchResultsPage` | — |

### 11.3. Чего не делать

- **Не выводить `Review` и `AggregateRating` о своей компании.** Отзывы, опубликованные самой
  компанией на своём сайте, поисковики считают «самопродвижением» и не показывают в сниппетах.
  Рейтинги площадок выводятся только как текст.
- Не выводить `HowTo` для «Этапов работы»: этот тип больше не поддерживается в выдаче Google.
- Не выводить `JobPosting`: у вакансий нет отдельных страниц. Если позже понадобится —
  включать только вместе с отдельными страницами вакансий.
- Google с 2023 года показывает FAQ-сниппеты только авторитетным государственным и медицинским
  сайтам. Разметку `FAQPage` всё равно делаем: она корректна, помогает поисковикам понимать
  страницу и проверяется валидатором Яндекса.

### 11.4. Проверка

Для каждого типа страницы с демо-контентом:
- JSON-LD — валидный JSON;
- нет дублирующихся `@id`;
- обязательные свойства на месте;
- разметка без ошибок в валидаторе Schema.org, валидаторе микроразметки Яндекс Вебмастера и Google
  Rich Results Test (FAQ, хлебные крошки, статья, Q&A, профиль, видео).

Автотест проверяет структуру (раздел 18). Ручную проверку внешними валидаторами опиши в отчёте
и приложи результаты, если есть доступ к сети.

**Во всех формах с персональными данными** (кроме поиска):
- отдельная обязательная галочка «Я даю согласие на обработку персональных данных» со ссылкой на
  страницу согласия (ссылка из настроек);
- галочка не отмечена заранее; без неё форма не отправляется — как в макетах;
- в форме отзыва — вторая галочка, согласие на распространение;
- ссылка «Как мы храним и защищаем данные — в политике конфиденциальности».

### 12.2. Обработка

- Отправка — `fetch` на REST-эндпоинт темы `POST /wp-json/trust/v1/forms/{type}` без
  перезагрузки. Если JavaScript выключен — обычная отправка формы на тот же обработчик с
  возвратом на страницу и сообщением.
- Проверка полей **на клиенте и на сервере** с теми же сообщениями, что в макетах. Поле с ошибкой
  подсвечивается, фокус переходит на первое такое поле; сообщение об успехе и кнопка «Отправить
  ещё» — как в макетах.
- Защита от спама:
  - скрытое поле-ловушка;
  - минимальное время заполнения;
  - ограничение частоты отправки с одного IP;
  - nonce;
  - капча: провайдер **Яндекс SmartCaptcha** с проверкой токена на сервере или «без капчи» — в
    настройках. Место под капчу в макетах уже есть.
- **Хранение:** каждая заявка — запись `lead`:
  - тип формы, все поля, страница отправки, UTM-метки и источник перехода (из cookie первой
    сессии), дата;
  - статус: «Новая», «В работе», «Закрыта»;
  - **факт согласия**: какие галочки, дата и время, адрес и дата редакции документа согласия.

  В админке — колонки «Дата», «Форма», «Имя», «Контакт», «Статус», фильтр по форме и статусу,
  экспорт выбранных в CSV. Заявки старше срока из настроек удаляются по WP-Cron (по умолчанию
  срок не задан — не удалять).
- **Уведомления:**
  - письмо через `wp_mail` получателям из настроек (свои получатели у каждой формы);
  - сообщение в Telegram, если заданы токен и chat_id;
  - POST JSON на вебхук CRM с подписью секретом, если задан.

  Ошибка любого канала не мешает сохранить заявку.
- **Вопрос SEO-специалисту:**
  - создаётся `question` со статусом «На утверждении»: имя, email, полный текст, дата;
  - заголовок — первые слова вопроса; редактор правит его перед публикацией;
  - когда ответ публикуется, спросившему автоматически уходит письмо со ссылкой на ответ (один
    раз, отметка в поле).
- **Отзыв:** создаётся `review` «На утверждении» с данными и согласиями. Контакты на сайт не
  выводятся.
- Заявки хранятся в базе сайта. Размещение сервера в России — требование заказчика к хостингу,
  тема не должна хранить данные заявок во внешних сервисах.
- Персональные данные **не отправляются** никуда, кроме каналов из настроек. Тема не подключает
  внешние сервисы, кроме капчи (если включена) и счётчиков после согласия.

## 13. Функции блога

- **Время чтения** — по числу слов текста и скорости из настроек, округление вверх, минимум 1 мин.
- **Просмотры** — счётчик в `trust_views`. Увеличивается запросом к REST после загрузки
  страницы, не чаще раза в сутки с одного браузера (метка в localStorage), боты не
  учитываются. Кеширование страниц не ломает подсчёт.
- **Лайки статей и комментариев** — REST-эндпоинт. Один лайк с браузера (метка в localStorage +
  cookie), повторное нажатие снимает лайк. Счётчик в метаполе. Защита от накрутки — ограничение
  частоты по IP.
- **Содержание статьи** — из заголовков H2 текста (автоматические `id` транслитом):
  - подсветка текущего раздела и «Прочитано N%» — как в макете;
  - на телефоне — свернутая панель над текстом;
  - пункт «Комментарии · N» в конце.
- **Сортировка в рубрике** «Новые / Популярные» — параметр `?sort=popular` (по лайкам, затем
  по дате). Переключатель работает без перезагрузки через REST, но и прямой адрес с параметром
  работает. У адреса с параметром canonical на рубрику без параметра.
- **Комментарии** — стандартные комментарии WordPress:
  - вёрстка по макету, ответы на 2 уровня;
  - модерация по умолчанию;
  - аватары — инициалы на цветном круге, Gravatar отключён.
- **Теги в статье** («Ключевые слова») ведут на страницы тегов.
- **Полоса рубрик** на странице рубрики — все непустые рубрики с числом статей. На телефоне
  листается одной строкой, текущая рубрика прокручивается в видимую область.

## 14. Cookie и счётчики

- Плашка (блок 17 из `holst-blokov/Cookies`):
  - внизу экрана при первом визите, кнопки «Принять», «Принять только обязательные»,
    «Отклонить всё»;
  - после выбора плашка скрывается, появляется кнопка «Изменить»;
  - тексты и ссылка на политику — из настроек.
- Выбор хранится в cookie `trust_consent` (категории `necessary`, `analytics`, `marketing`, дата,
  версия) на срок из настроек (по умолчанию 365 дней). Блок «Настройки cookie» на странице
  политики читает и меняет этот же выбор.
- Код счётчиков (например, Яндекс Метрика) и рекламных пикселей задаётся в настройках.
  Вставляется **только после согласия** на соответствующую категорию — сразу после нажатия, без
  перезагрузки.
- Встраиваемые видео и интерактивная карта загружаются только по клику посетителя.

## 15. Производительность, доступность, адаптивность

**Производительность** (на демо-контенте, мобильный профиль Lighthouse):
- Performance ≥ 90, LCP < 2,5 с, CLS < 0,1, INP < 200 мс;
- на фронтенде нет jQuery, нет блокирующих скриптов в `<head>`, JS подключается с `defer` или как
  модули и только для блоков на странице;
- CSS блока подключается, только если блок есть на странице; общий CSS — не больше ~40 КБ без сжатия;
- шрифты — локальные woff2 (кириллица + латиница), `font-display: swap`, предзагрузка
  основного начертания. Взять из npm-пакетов `@fontsource/unbounded`, `@fontsource/onest`,
  `@fontsource/jetbrains-mono` (или с Google Fonts) вместе с файлами лицензии OFL. Если сети нет —
  остановись и сообщи;
- отключить лишнее: emoji-скрипты, oEmbed-discovery, RSD/WLW-ссылки, глобальные стили ядра для
  неиспользуемых блоков;
- картинки — `srcset`/`sizes`, WebP/AVIF через стандартную обработку WordPress,
  `width`/`height` у всех `<img>`.

**Доступность:** уровень WCAG 2.1 AA, как в макетах:
- контраст ≥ 4,5:1;
- видимый фокус;
- навигация с клавиатуры по меню, аккордеонам, вкладкам, карусели, фильтрам, калькулятору,
  модальным окнам;
- `aria-expanded`, `aria-selected`, `aria-pressed`, `aria-current`, `aria-live` для счётчиков
  фильтров и сообщений форм;
- ссылка «Перейти к содержимому»;
- `lang="ru"`.

**Адаптивность:** поведение на ширинах 280–1440+ px — как в макетах и их README:
- меню-бургер уже 1180 px;
- первые экраны на всю ширину до 640 px;
- полосы фильтров и рубрик листаются строкой;
- сетки 3/2/1 колонки **без одиноких карточек в последнем ряду** там, где в макетах это решено;
- таблицы превращаются в карточки;
- закреплённые боковые колонки становятся обычными на планшете и при низком окне;
- зоны нажатия ≥ 44 px, поля 16 px, нет прокрутки вбок.

## 16. Удобство редактора (админка)

- Окно выбора типа страницы и наборы блоков (раздел 6).
- **Разрешённые блоки** (фильтр `allowed_block_types_all`):
  - на страницах — все блоки темы и ограниченный набор стандартных: абзац, заголовок, список,
    цитата, картинка, таблица, разделитель, кнопки, паттерны;
  - у статей и ответов — стандартные текстовые блоки, `trust/video`, `trust/image`,
    `trust/how-i-would` (только ответы), `trust/notice`, `trust/posts`;
  - у кейсов — блоки кейса и текстовые.

  Блоки, которые имеют смысл только на своём типе страницы («Кейсы», «Ответы SEO-специалистов»),
  в остальных типах скрыты.
- **Синхронизированные паттерны** разрешены: блок, одинаковый на многих страницах (например,
  «Кнопка связи»), правится в одном месте.
- **Превью блоков** в редакторе совпадает с сайтом: тот же `render.php` и CSS. Интерактивные
  блоки в редакторе показывают раскрытое или первое состояние, чтобы все поля было видно.
- **Подсказки в полях:**
  - рекомендуемая длина текста;
  - размеры и пропорции картинок (например «16:9, не меньше 1600×900»);
  - для чего поле.

  Обязательные поля отмечены.
- Колонки в списках админки:
  - кейсы — главный, услуги, отрасль;
  - вопросы — статус, спросивший, тема, специалист;
  - отзывы — вид, автор, услуга, статус;
  - заявки — раздел 12.
- Роли: «Редактор» управляет всем контентом, заявками и вкладками настроек с контентом.
  «Администратор» — плюс технические настройки.
- Счётчики в меню админки: число новых заявок и вопросов на утверждении.

## 17. Демо-контент

WP-CLI команда `wp trust demo import` (и `wp trust demo remove`) создаёт сайт, который выглядит
как макеты:

- все страницы по типам с заполненными блоками — тексты, цифры и заглушки `[…]` из макетов;
- статьи блога (не меньше 21, чтобы была пагинация), рубрики и теги из макетов;
- кейсы (9 из портфолио), отзывы, сотрудников, вакансии, вопросы с ответами (не меньше 21);
- меню (Приложение Б) и настройки сайта (контакты-заглушки, реквизиты-заглушки);
- картинки из папок `images/` экспортов: обложки, скриншоты, графики, фото-заглушки.
  Загрузка — в медиатеку с alt из макетов.

Все демо-записи помечены метаполем, чтобы `demo remove` удалял только их. Повторный импорт не
создаёт дублей.

## 18. Тестирование и критерии приёмки

### 18.1. Автотесты (`wp-theme/tests/`)

1. **Визуальная сверка** (Playwright).
   - Каждая страница сайта с демо-контентом сравнивается со своим эталонным HTML-экспортом из
     репозитория на ширинах 390 и 1280 px (и 768 для страниц с особой планшетной раскладкой).
   - Допустимое расхождение — до 2 % пикселей на экран. Динамические места (даты, счётчики)
     маскируются.
   - Приложить отчёт со скриншотами «эталон / тема / разница».
2. **Адаптивность** на 17 размерах: 280×653, 320×568, 360×740, 375×667, 390×844, 412×915,
   430×932, 600×960, 768×1024, 820×1180, 1024×1366, 667×375, 844×390, 932×430, 1024×768,
   1280×800, 1440×900. Проверяется:
   - нет прокрутки вбок и элементов за краем экрана;
   - нет обрезанного текста;
   - зоны нажатия ≥ 44 px на ширинах < 1024;
   - текст ≥ 12 px, поля ≥ 16 px;
   - нет растянутых картинок;
   - нет ошибок в консоли;
   - нет одиноких карточек в сетках (там, где они исключены в макетах).
3. **Интерактив**:
   - меню и бургер, выпадающие списки, Esc;
   - аккордеоны блоков 4 и 10;
   - этапы, свайп-кнопка (мышь, касание, Enter), калькулятор (все шаги, формула, результат);
   - карусель;
   - фильтры портфолио, команды, отзывов, вакансий (счётчики, пустой результат, сброс);
   - «Показать ещё»;
   - вкладки графиков кейса, сортировка рубрики, фильтр тега;
   - содержание статьи и документа;
   - лайки и просмотры;
   - плашка и настройки cookie (скрипты счётчиков появляются только после согласия);
   - печать документа.
4. **Формы**: каждая форма отправляется с валидными данными, создаётся `lead` (и `question` /
   `review`, где нужно), уходит письмо (тестовый перехватчик почты), неверные данные и пустое
   согласие отклоняются на сервере, ловушка и лимит частоты срабатывают.
5. **SEO**:
   - у каждой страницы ровно один H1, совпадающий с SEO-полем;
   - title, description, canonical, robots и OG соответствуют правилам раздела 10;
   - у всех `<img>` с содержанием непустой alt;
   - 404 отдаёт HTTP 404;
   - карта сайта не содержит исключённых записей;
   - теги ниже порога — `noindex`.
6. **Микроразметка**: JSON-LD парсится, обязательные свойства на месте, нет дублей `@id`,
   `FAQPage` содержит ровно вопросы видимых блоков FAQ, `BreadcrumbList` совпадает с видимыми
   крошками.
7. **Доступность**: axe-core без нарушений уровней critical и serious.
8. **Код**: `phpcs` (WPCS) без ошибок, `php -l` по всем файлам, нет PHP-предупреждений и
   уведомлений при `WP_DEBUG=true`, проверка темы плагином Theme Check без критичных замечаний.
9. **Lighthouse** (мобильный): показатели из раздела 15 для главной, услуги, статьи, портфолио,
   кейса.

### 18.2. Критерии приёмки

- [ ] Все секции всех макетов реализованы блоками или шаблонами, инвентарь заполнен без
      пропусков.
- [ ] Ни один видимый посетителю текст, картинка или ссылка из макетов не зашиты в код темы.
- [ ] Новая страница создаётся через выбор типа, набор блоков подставляется, блоки

- [ ] У страниц, статей, кейсов, ответов, сотрудников, рубрик и тегов заполняются title,

- [ ] Автотесты раздела 18.1 проходят. Отчёт со скриншотами и результатами приложен.
